# convo-eval — Specification

> Multi-turn agent testing with LLM-simulated users for TypeScript.

## 1. Problem statement

Most agent testing today is single-turn: given input X, does output Y meet criteria Z? But agents in production operate across multi-turn conversations where failures are experiential — context drift, knowledge loss, infinite loops, and instruction drift compound across turns in ways that single-turn metrics cannot detect.

Google's ADK provides the most complete multi-turn evaluation system via its `ConversationScenario` + `UserSimulatorProvider` design, but it's Python-only and tightly coupled to the ADK runtime. The TypeScript ecosystem has no equivalent standalone package.

`convo-eval` fills this gap: a framework-agnostic, provider-agnostic TypeScript library for multi-turn agent evaluation using LLM-simulated users and natural language test scenarios.

## 2. Design principles

1. **Intent over script.** Test scenarios define *what the user wants to accomplish*, not the exact messages. Tests are resilient to changes in agent phrasing, question ordering, and internal logic.
2. **Framework-agnostic.** Works with any agent that accepts a string and returns a response. No dependency on ADK, LangChain, Vercel AI SDK, or any specific agent framework.
3. **Provider-agnostic.** The simulator LLM and evaluator LLM are injectable functions, not hardcoded to any provider. Compatible with OpenAI, Anthropic, Google, local models, or custom APIs.
4. **Vitest/Jest-native.** Designed to plug into existing TypeScript test pipelines with custom matchers.
5. **Minimal core, composable evaluators.** Ship a small set of built-in evaluators. Users can define custom evaluators via a simple interface.

## 3. Core data model

### 3.1 ConversationScenario

The primary input. Defines what to test without specifying the exact conversation flow.

```typescript
interface ConversationScenario {
  /** Fixed first user message sent to the agent. */
  startingPrompt: string;

  /**
   * Natural language description of the goals the simulated user must achieve.
   * The simulator LLM uses this plus conversation history to generate each
   * subsequent user message.
   *
   * Example: "Book a one-way flight from SFO to LAX for next Tuesday.
   * Prefer a morning flight under $150. If the agent finds options,
   * pick the cheapest one. Then ask about car rental at LAX."
   */
  conversationPlan: string;

  /** Optional persona controlling simulated user behavior. */
  userPersona?: UserPersona;

  /** Maximum number of turns before forced termination. Default: 10. */
  maxTurns?: number;

  /** Custom stop signal the simulator emits when the plan is complete. Default: "</finished>". */
  stopSignal?: string;
}
```

### 3.2 UserPersona

Controls how the simulated user communicates — not what they want, but how they express it.

```typescript
interface UserPersona {
  /** Persona identifier. E.g., "frustrated-customer", "expert", "novice". */
  name: string;

  /** Free-text description injected into the simulator system prompt. */
  description: string;

  /** Specific behavioral traits the persona exhibits. */
  behaviors: PersonaBehavior[];
}

interface PersonaBehavior {
  /** Behavior name. E.g., "proactive_information_sharing". */
  name: string;

  /** What this behavior means in practice. */
  description: string;

  /**
   * Natural language rubrics that, if satisfied, indicate the simulator
   * VIOLATED this behavior. Used by the persona adherence evaluator.
   *
   * Example for a "terse" behavior:
   * ["The user's message exceeds 50 words",
   *  "The user provides information that was not asked for"]
   */
  violationRubrics: string[];
}
```

### 3.3 Built-in personas

Ship three personas matching ADK's defaults. Users can define custom personas.

| Persona    | Key behaviors                                              |
| ---------- | ---------------------------------------------------------- |
| `EXPERT`   | Detail-oriented, proactively provides all relevant details |
| `NOVICE`   | Goal-oriented, waits to be asked, gives minimal info       |
| `EVALUATOR`| Professional tone, focused, asks targeted questions        |

### 3.4 Turn and Transcript

The output of a simulation run.

```typescript
interface Turn {
  /** Turn index (0-based). */
  index: number;

  /** The user message (generated by simulator or starting_prompt for turn 0). */
  userMessage: string;

  /** The agent's text response. */
  agentResponse: string;

  /** Tool calls made by the agent during this turn. */
  toolCalls: ToolCall[];

  /** Duration of this turn in milliseconds. */
  durationMs: number;
}

interface ToolCall {
  /** Tool/function name. */
  name: string;

  /** Arguments passed to the tool. */
  args: Record<string, unknown>;

  /** Tool result (if captured). */
  result?: unknown;
}

interface SimulationResult {
  /** Full conversation transcript. */
  turns: Turn[];

  /** Whether the simulator reached the stop signal (plan completed). */
  planCompleted: boolean;

  /** Reason for termination: "stop_signal" | "max_turns" | "error". */
  terminationReason: string;

  /** Total token usage across all simulator + agent calls. */
  tokenUsage: { simulator: number; agent: number };

  /** Total cost estimate (if provider reports pricing). */
  costEstimate?: { simulator: number; agent: number };
}
```

## 4. Simulation engine

### 4.1 UserSimulator

The core loop that drives the simulated conversation.

```typescript
interface UserSimulatorConfig {
  /** LLM function used to generate simulated user messages. */
  simulatorLLM: LLMFunction;

  /** Optional custom system prompt override for the simulator. */
  systemPromptOverride?: string;
}

/**
 * Generic LLM function signature. Accepts messages, returns a string.
 * This is the only integration point — any provider works.
 */
type LLMFunction = (messages: LLMMessage[]) => Promise<string>;

interface LLMMessage {
  role: "system" | "user" | "assistant";
  content: string;
}
```

### 4.2 Simulation loop

The simulation loop is a generator that yields turns as they complete, enabling real-time progress reporting.

```
┌──────────────────────────────────────────────────────┐
│  Turn 0                                              │
│  ┌─────────────────┐      ┌───────────────────────┐  │
│  │ starting_prompt  │ ───► │ Agent under test       │  │
│  │ (used as-is)     │      │ responds + tool calls  │  │
│  └─────────────────┘      └───────────────────────┘  │
├──────────────────────────────────────────────────────┤
│  Turn 1..N                                           │
│  ┌─────────────────┐      ┌───────────────────────┐  │
│  │ Simulator LLM    │ ───► │ Agent under test       │  │
│  │ (plan + history   │      │ responds + tool calls  │  │
│  │  + persona)       │      │                        │  │
│  └─────────────────┘      └───────────────────────┘  │
│         ▲                          │                  │
│         └──────────────────────────┘                  │
│              history appended                         │
├──────────────────────────────────────────────────────┤
│  Termination                                         │
│  Stop if: stop_signal emitted │ maxTurns reached     │
│           │ error thrown                              │
└──────────────────────────────────────────────────────┘
```

### 4.3 Simulator system prompt

The default system prompt template for the simulator LLM. The package ships this as a default, but it can be overridden entirely.

Template variables:

- `{conversationPlan}` — from the scenario
- `{personaDescription}` — from the persona (or "a typical user" if none)
- `{personaBehaviors}` — formatted list of behavior descriptions
- `{stopSignal}` — the termination marker
- `{conversationHistory}` — formatted transcript so far

Default template (conceptual):

```
You are simulating a user interacting with an AI agent.

Your goal: Follow the conversation plan below. Generate realistic user
messages that pursue these goals. Do NOT break character.

PLAN:
{conversationPlan}

PERSONA:
{personaDescription}

BEHAVIORS:
{personaBehaviors}

When ALL goals in the plan have been achieved, output exactly: {stopSignal}

Generate only the next user message. Do not include any meta-commentary,
reasoning, or role labels.
```

### 4.4 Agent adapter

The agent under test is provided as a simple async function. This keeps the library decoupled from any framework.

```typescript
/**
 * Adapter for the agent under test.
 * Accepts a user message and conversation history,
 * returns the agent's response with tool calls.
 */
type AgentFunction = (
  message: string,
  history: Turn[]
) => Promise<AgentResponse>;

interface AgentResponse {
  text: string;
  toolCalls: ToolCall[];
}
```

Users wrap their agent (ADK, LangGraph, Vercel AI, raw API calls, etc.) in this adapter. The README will include examples for common frameworks.

## 5. Evaluation system

### 5.1 Evaluator interface

All evaluators implement the same interface. This enables composition and custom evaluators.

```typescript
interface Evaluator {
  /** Unique evaluator name. */
  name: string;

  /** Evaluate the simulation result against the scenario. */
  evaluate(
    result: SimulationResult,
    scenario: ConversationScenario,
    llm?: LLMFunction
  ): Promise<EvalResult>;
}

interface EvalResult {
  /** Evaluator name. */
  evaluator: string;

  /** Score from 0.0 (worst) to 1.0 (best). */
  score: number;

  /** Whether the score meets or exceeds the threshold. */
  pass: boolean;

  /** Human-readable explanation of the score. */
  reason: string;

  /** Optional per-turn breakdown. */
  perTurn?: TurnEvalResult[];
}

interface TurnEvalResult {
  turnIndex: number;
  score: number;
  reason: string;
}
```

### 5.2 Built-in evaluators

#### 5.2.1 Plan completion

LLM-as-judge evaluator. Sends the full transcript and the conversation plan to a judge LLM and asks: "Were all goals in the plan achieved by the end of the conversation? Score 1.0 if all goals met, 0.5 if partially met, 0.0 if not met. Explain your reasoning."

```typescript
const planCompletion = createPlanCompletionEvaluator({
  judgeLLM: myLLM,
  threshold: 0.8,
});
```

#### 5.2.2 Tool trajectory

Deterministic evaluator. Compares the actual sequence of tool calls against an expected sequence. Supports three match modes:

- **`exact`** — perfect match of names, args, and order.
- **`in_order`** — expected tools appear in order but other calls may be interleaved.
- **`any_order`** — expected tools all appear but order doesn't matter.

Score = number of matching invocations / total invocations.

```typescript
const trajectory = createTrajectoryEvaluator({
  expected: [
    { name: "search_flights", args: { from: "SFO", to: "LAX" } },
    { name: "book_flight" },
  ],
  matchMode: "in_order",
  threshold: 1.0,
});
```

#### 5.2.3 Response quality

LLM-as-judge evaluator. Scores each agent response against a natural language rubric provided by the user.

```typescript
const quality = createResponseQualityEvaluator({
  judgeLLM: myLLM,
  rubric: "The agent should be helpful, concise, and never hallucinate information. Score 1.0 for excellent, 0.5 for acceptable, 0.0 for poor.",
  threshold: 0.7,
});
```

#### 5.2.4 Persona adherence

LLM-as-judge evaluator. Checks whether the simulator's generated user messages followed the persona's behavioral constraints by evaluating each turn against the `violationRubrics`. This evaluator validates the *simulation quality itself*, not the agent.

#### 5.2.5 Conversation quality metrics

A set of conversation-level evaluators inspired by DeepEval's multi-turn metrics:

- **Knowledge retention** — does the agent remember information the user provided in earlier turns?
- **Conversation relevancy** — using a sliding window of prior turns, does each response stay on topic?
- **Role adherence** — does the agent stay consistent with its system prompt persona throughout?

### 5.3 Custom evaluators

Users can define evaluators using the `Evaluator` interface or a convenience helper:

```typescript
const customEval = defineEvaluator({
  name: "no-apology-overuse",
  async evaluate(result) {
    const apologyCount = result.turns.filter(
      t => t.agentResponse.toLowerCase().includes("i apologize")
    ).length;
    const score = Math.max(0, 1 - apologyCount / result.turns.length);
    return { score, pass: score >= 0.8, reason: `Agent apologized in ${apologyCount}/${result.turns.length} turns` };
  },
});
```

## 6. Test runner integration

### 6.1 Vitest/Jest custom matchers

```typescript
import { installMatchers } from "convo-eval/vitest";

installMatchers();

test("support agent handles frustrated customer", async () => {
  await expect(myAgentFn).toPassConversationScenario(
    {
      startingPrompt: "I need to return a defective laptop.",
      conversationPlan:
        "Express frustration, ask about return policy, provide order #1234 when asked, request replacement instead of refund.",
      userPersona: FRUSTRATED_CUSTOMER,
      maxTurns: 8,
    },
    {
      simulatorLLM: openaiChat("gpt-4o-mini"),
      evaluators: [planCompletion(), responseQuality({ rubric: "..." })],
      threshold: 0.8,
    }
  );
});
```

### 6.2 Programmatic API

For CI/CD integration or custom test harnesses.

```typescript
import { simulate, evaluate } from "convo-eval";

const result = await simulate({
  scenario: myScenario,
  agentFn: myAgentAdapter,
  simulatorLLM: openaiChat("gpt-4o-mini"),
});

const evalResults = await evaluate(result, myScenario, {
  evaluators: [planCompletion(), trajectory({ expected: [...] })],
});

console.log(evalResults.summary);
// { overall: "PASS", evaluators: [{ name: "plan-completion", score: 0.95, pass: true }, ...] }
```

### 6.3 CLI

Optional CLI for running scenarios defined in JSON/YAML files.

```bash
npx convo-eval run scenarios.json --agent ./my-agent-adapter.ts
npx convo-eval run scenarios.json --agent ./my-agent-adapter.ts --output results.json
```

## 7. Scenario definition format

Scenarios can be defined in JSON or YAML for use with the CLI or batch evaluation.

```yaml
# scenarios.yaml
scenarios:
  - name: "flight-booking-happy-path"
    startingPrompt: "I need to book a flight."
    conversationPlan: |
      Book a one-way flight from SFO to LAX for next Tuesday.
      Prefer a morning flight under $150.
      If options are found, pick the cheapest.
    userPersona: expert
    maxTurns: 8

  - name: "refund-frustrated-customer"
    startingPrompt: "I want my money back!"
    conversationPlan: |
      Demand a refund for order #4821.
      Initially refuse to provide the order number.
      Eventually provide it when pressed.
      Accept the refund if offered.
    userPersona:
      name: frustrated
      description: "Short sentences, impatient, uses caps for emphasis."
      behaviors:
        - name: terse
          description: "Keeps messages under 20 words."
          violationRubrics:
            - "The user's message exceeds 30 words."
    maxTurns: 10

evalConfig:
  simulatorModel: "gpt-4o-mini"
  evaluators:
    - name: plan-completion
      threshold: 0.8
    - name: tool-trajectory
      matchMode: in_order
      threshold: 1.0
    - name: response-quality
      rubric: "Agent should be empathetic, accurate, and resolve the issue."
      threshold: 0.7
```

## 10. Non-goals (v1)

- **Not a framework.** convo-eval does not provide agent building primitives, orchestration, or tool registration. It tests agents built with other tools.
- **No built-in MCP/protocol support.** Agent interaction is via the `AgentFunction` adapter — the user wraps their agent.
- **No GUI.** v1 is CLI + programmatic API. A web-based trace viewer may come later.
- **No persistent storage.** Results are returned in memory or written to JSON. No database.
- **No parallel scenario execution.** Run scenarios sequentially in v1. Users can parallelize via their test runner.

## 11. Future considerations (post-v1)

- **Dry-run mode.** Run the simulator without evaluators to inspect the conversation before scoring.
- **Golden dataset generation.** Capture a simulation run as a golden dataset for regression testing (static turn-by-turn tests derived from a dynamic simulation).
- **Streaming support.** Yield evaluation results per-turn as the simulation progresses.
- **Scenario fuzzing.** Automatically generate variations of a scenario (different personas, parameter values, edge cases) to broaden coverage.
- **Cost tracking.** Report token usage and estimated cost per scenario run.
- **Trace viewer.** Web UI for inspecting simulation transcripts with per-turn scores, tool call visualization, and evaluator explanations.
